# `/wechat-article` · 위챗 공식계정 글 작성

> 📄 원문: [skills/wechat-article.md](https://github.com/xbtlin/ai-berkshire/blob/main/skills/wechat-article.md) · 원문은 중국어이며, 아래는 한국어 번역입니다.

::: tip 한눈에 보기
- **무엇을 하나요?** 주제를 깊이 조사한 뒤 작가 에이전트가 초안을 쓰고, 편집자·독자 에이전트가 동시에 검토해서 바로 게시할 수 있는 위챗 공식계정 글을 완성해요.
- **언제 쓰나요?** 논문·기술 해설이나 투자 주제를 깊이 있으면서도 읽기 쉬운 장문 글로 풀어내고 싶을 때 써요.
- **사용 예:** `/wechat-article 대모델 OPD 기술 해설` (원문 예시: `大模型OPD技术解读`, `为什么巴菲特不买科技股`)
- **결과물:** `reports/` 아래(기술 주제는 `reports/AI产业研究/`, 투자 주제는 `reports/{회사명}/`)에 완성 원고 md 파일이 만들어지고, 그림은 `assets/{주제약칭}/`에 저장돼요.
- **핵심 특징:** 작가·편집자·독자 3중 시점 검토, 논문 원본 그림을 고해상도로 추출해 실제 삽입, LaTeX 수식마다 쉬운 말 풀이, 데이터 날조·AI 말투 금지 같은 글쓰기 레드라인이 있어요.
:::

## 번역 전문

**원제:** 위챗 공식계정 글: 작가-편집자-독자 3 에이전트 협업

$ARGUMENTS 에 대해 심층 조사를 수행하고, 바로 게시할 수 있는 위챗 공식계정 글 한 편을 산출합니다. 세 에이전트가 각자 역할을 맡습니다. 작가는 깊이 있는 초안을 쓰고, 편집자는 구조와 표현을 다듬으며, 독자는 대상 독자의 시각에서 글을 검토합니다.

**지원 입력 형식**: 주제 설명. 예: `大模型OPD技术解读`(대모델 OPD 기술 해설), `Qwen3技术报告解读`(Qwen3 기술 보고서 해설), `为什么巴菲特不买科技股`(버핏은 왜 기술주를 사지 않는가)

---

## 설계 이념

좋은 공식계정 글은 세 가지 차원을 동시에 충족해야 합니다.
1. **깊이** — 시간을 들여 끝까지 읽은 사람에게 부끄럽지 않을 것 (작가 담당)
2. **가독성** — 구조가 명확하고 리듬이 좋으며 독자가 중도 포기하지 않을 것 (편집자 담당)
3. **정말로 이해할 수 있을 것** — 대상 독자가 중간에 포기하지 않을 것 (독자 담당)

혼자 쓰는 글은 '자기만족'에 빠지기 쉽습니다. 쓴 사람은 명확하다고 느끼지만 읽는 사람은 이해하지 못합니다. 3 에이전트 협업의 본질은 **외부 시각을 강제로 끌어들이는 것**입니다.

---

## 1단계: 조사와 자료 수집

### 첫 번째 작업: 글의 포지셔닝 명확히 하기

쓰기 시작하기 전에 먼저 다음 정보를 확인합니다(사용자가 지정하지 않았다면 먼저 물어볼 것).

| 차원 | 확인할 내용 | 기본값 |
|------|---------|--------|
| **대상 독자** | 기술적 배경 수준 | 기술 배경은 약간 있으나 해당 분야 전문가는 아님 |
| **글의 깊이** | 교양/중간 깊이/하드코어 | 중간 깊이(수식은 있되 명확히 설명할 것) |
| **글의 길이** | 글자 수 범위 | 3000-4000자 |
| **원본 논문/자료 다운로드 필요 여부** | PDF/삽화 필요 | 예 |
| **글쓰기 스타일** | 격식체/대화체/날카로움 | 대화체(똑똑한 친구에게 쓰듯이) |

### 두 번째 작업: 심층 조사

Agent 도구를 사용해 2~3개의 조사 에이전트를 **병렬로** 실행하여 충분한 자료를 수집합니다.

**조사 에이전트 A: 핵심 내용 조사**
- 논문 해설인 경우: 논문 PDF를 다운로드하고 핵심 기여, 주요 도표, 실험 결과를 추출합니다
- 기술 주제인 경우: 최신 진전, 주요 논문, 기술 세부사항을 검색합니다
- 비즈니스/투자 주제인 경우: 최신 데이터, 산업 보고서, 경쟁 구도를 검색합니다

**조사 에이전트 B: 산업 배경과 응용**
- 해당 기술/주제의 산업 현장 적용 현황을 검색합니다
- 어떤 회사들이 쓰고 있는가? 효과는 어떤가?
- 최신 발전 추세와 이정표가 된 사건

**조사 에이전트 C(선택): 경쟁 제품/비교 조사**
- 유사 방법/제품과의 비교
- 역사적 발전 흐름
- 향후 진화 방향

### 세 번째 작업: 자료 프레임 정리

조사 에이전트가 모두 완료되면 다음을 정리합니다.
1. **핵심 논지** (글이 전달하려는 핵심 메시지를 한 문장으로 요약)
2. **핵심 데이터** (가장 임팩트 있는 데이터 포인트 3~5개)
3. **삽화 목록** (어떤 그림이 필요하고, 출처는 무엇인지)
4. **글 개요** (6~8개 장의 제목과 핵심 내용)

## 2단계: 작가 에이전트가 초안 작성

Agent 도구를 사용해 **작가 에이전트**를 실행하고, 상세한 작성 지시를 제공합니다.

### 작가 에이전트의 프롬프트 템플릿

```
당신은 깊이 있는 기술 글을 쓰는 작가(Author Agent)이며, 위챗 공식계정 글 한 편을 써야 합니다.

## 대상 독자
{첫 번째 작업에서 확인한 독자 페르소나에 따라}

## 글쓰기 스타일 요구사항
- 순수 중국어로 표현하고 중국어와 영어를 섞어 쓰지 말 것(기술 용어는 처음 등장할 때 영어를 병기하고, 이후에는 중국어 사용)
- 학술 논문 번역이 아니라, 똑똑한 친구에게 보여 주는 기술 교양 글처럼 쓸 것
- 비유를 활용해 이해를 돕되, 비유는 적절하고 진부하지 않을 것
- 핵심 수식/데이터는 넣되, 각각을 모두 쉬운 말로 설명할 것
- 이모지를 쓰지 말 것
- 문단은 4줄을 넘기지 말 것(공식계정 읽기 환경)

## 핵심 내용
{정리된 자료, 데이터, 논지}

## 글 구조 요구사항
1. **도입부(처음 3문단)**: 반드시 강한 훅이 있어야 함 — 데이터의 충격이나 직관에 반하는 결론으로 시작하고, 온건한 비유로 시작하지 말 것
2. **배경**: 이 일이 왜 중요한가? 어떤 문제를 해결하는가?
3. **핵심 내용(2~3절)**: 기술적 깊이는 여기서 드러내되, 모든 기술 포인트에 '쉬운 말 번역'을 붙일 것
4. **실증/사례**: 데이터와 사례로 말하고, 공론은 피할 것
5. **산업 영향/전망**: 이 일이 산업에 어떤 의미가 있는가
6. **결말**: 캡처해서 공유하기 좋은, 전파력 있는 한 문장의 판단으로 마무리할 것

## 삽화 요구사항
- 논문 해설 글: 반드시 논문 PDF에서 원본 그림을 추출해 `![설명](상대경로)` 로 글에 직접 삽입하고, [그림X: 설명] 같은 자리표시자를 쓰지 말 것
- 추출 방법: pdftoppm으로 PDF 페이지를 고해상도 PNG(최소 900 DPI)로 렌더링한 뒤, PIL로 대상 도표 영역을 잘라낼 것
- 그림 한 장당 500KB 이상으로 고화질을 보장할 것
- 이미지는 모두 `assets/{주제약칭}/` 디렉터리에 저장할 것
- 논문이 아닌 글: 삽화가 필요하면 적절한 이미지를 검색·다운로드해 마찬가지로 직접 삽입할 것

## 수식 요구사항
- 모든 수학 수식은 LaTeX 형식을 사용할 것: 인라인은 `$...$`, 독립 수식은 `$$...$$`
- 수식을 순수 텍스트로 쓰는 것을 금지함(예: `> D_KL(P || Q) = ...`). 반드시 LaTeX 렌더링 형식을 쓸 것
- 각 수식 뒤에는 여전히 '쉬운 말 번역'을 붙일 것

완전한 글 초안을 약 {목표 글자 수}자로 작성하세요.
```

### 작가 에이전트 완료 후

초안 파일이 생성되었는지 확인하고, 전문을 읽어 내용이 완전한지 확인합니다.

## 3단계: 편집자 에이전트 + 독자 에이전트 병렬 검토

초안이 완성되면 Agent 도구를 사용해 **같은 메시지 안에서** 편집자 에이전트와 독자 에이전트를 함께 실행합니다.

### 편집자 에이전트의 프롬프트 템플릿

```
당신은 노련한 공식계정 편집자(Editor Agent)입니다. 다음 글을 정밀하게 다듬고 검토하세요.

## 검토 기준
1. **제목**: 위챗 모멘트(朋友圈)에서 클릭을 유도할 수 있는가? 잘리지는 않는가(30자 초과)?
2. **도입부**: 처음 3문단이 독자를 붙잡을 수 있는가? 훅이 충분히 강한가?
3. **구조**: 논리 흐름이 매끄러운가? 비약이나 단절은 없는가?
4. **깊이와 가독성의 균형**: 수식/기술 부분이 정말 쉽게 풀렸는가? '쉬운 척하지만 제대로 설명하지 않은' 곳은 없는가?
5. **리듬**: 너무 긴 문단은 없는가? 각 절의 길이는 적절한가?
6. **삽화**: 이미지가 실제로 삽입되었는가(자리표시자가 아닌가)? 독자가 시각적 도움을 가장 필요로 할 때 등장하는가?
7. **결말**: 전파력이 있는가? 독자가 다 읽고 나서 공유하고 싶어질까?

## 글 전문
{완전한 초안}

## 출력 형식
1. 총평(3~5문장)
2. 제목 수정 제안(대안 2~3개 제시)
3. 절별 수정 제안('원문 → 이렇게 수정 제안'의 구체적 대조로 제시)
4. 가장 중요한 개선점 3가지
```

### 독자 에이전트의 프롬프트 템플릿

```
당신은 {대상 독자 페르소나}(Reader Agent)입니다. 독자의 시각에서 다음 글을 검토하세요.

## 당신의 배경
{대상 독자의 지식 수준과 읽기 습관을 구체적으로 기술}

## 글 전문
{완전한 초안}

## 다음 질문에 답하세요
1. 처음 3문단을 읽고 계속 읽겠습니까? 왜 그렇습니까?
2. 어떤 부분이 '이해가 안 되거나' '다시 읽어야 이해되었습니까'? 구체적으로 어떤 문장입니까?
3. 기술/수식 부분을 이해했습니까? '쉬운 말 번역'이 도움이 되었습니까?
4. 글의 핵심 비유는 적절합니까? 더 나은 비유가 있습니까?
5. 너무 깁니까, 너무 짧습니까? 어디에서 인내심을 잃겠습니까?
6. 다 읽은 뒤 글의 핵심 관점을 한 문장으로 요약할 수 있습니까?
7. 이 글을 공유하겠습니까? 공유할 때 뭐라고 말하겠습니까?
8. 알고 싶었지만 글에서 다루지 않은 질문이 있습니까?
```

## 4단계: 최종 원고 확정

### 첫 번째 작업: 두 에이전트의 피드백 종합

다음과 같이 자주 나오는 문제에 중점을 둡니다.

| 문제 유형 | 편집자의 흔한 피드백 | 독자의 흔한 피드백 | 처리 방식 |
|---------|------------|------------|---------|
| 도입부가 약함 | 훅이 충분히 강하지 않음 | 처음 3문단에서 계속 읽을 동력이 없음 | 데이터/직관에 반하는 결론으로 도입부를 다시 씀 |
| 기술 문단이 독자를 쫓아냄 | 수식이 너무 빽빽함 | 어떤 문단은 세 번 다시 읽어야 함 | 수식을 삭제하거나 그림으로 바꾸고, 더 직관적인 비유를 추가 |
| 리듬이 늘어짐 | 어떤 절이 너무 김 | 어느 지점에서 인내심을 잃음 | 합치거나 줄임(특히 후반부에서 반복되는 기술 설명) |
| 결말이 힘이 없음 | 전파력이 부족함 | 공유하지 않을 것 | 캡처해서 퍼뜨릴 만한 한 문장의 판단으로 다시 씀 |
| 개념 비약 | 논리에 단절이 있음 | 어느 지점에서 '갑자기 이해가 안 됨' | 연결 문장이나 배경 설명을 보충 |

### 두 번째 작업: 수정 실행

피드백에 따라 글을 다시 씁니다. 핵심 수정 원칙은 다음과 같습니다.

1. **편집자와 독자가 모두 지적한 문제는 반드시 고칩니다**
2. **편집자만 지적한 문제는 대체로 고칩니다**(편집자의 전문적 판단은 보통 정확함)
3. **독자만 지적한 문제는 상황을 보고 고칩니다**(독자 피드백은 실제 경험을 대표하지만, 모든 항목에 대응할 필요는 없음)
4. **둘이 상충할 때는 독자 쪽을 따릅니다**(편집자는 완벽을 추구하지만, 독자 경험이 최종 기준임)

### 세 번째 작업: 삽화 추출

논문 해설 글은 원고 확정 전에 반드시 삽화 추출을 마쳐야 합니다.

1. **렌더링**: `pdftoppm -png -r 900 -f {페이지번호} -l {페이지번호} 논문.pdf /tmp/page`(900 DPI부터 시작하고, 이미지가 500KB에 못 미치면 1200 또는 1500 DPI로 올릴 것)
2. **위치 파악**: 먼저 150 DPI로 전체 페이지를 렌더링해 각 도표의 픽셀 좌표를 눈으로 확인합니다
3. **자르기**: PIL로 좌표에 따라 잘라내고 `compress_level=1`로 저장해 각 이미지가 ≥ 500KB가 되도록 합니다
4. **저장**: `assets/{주제약칭}/` 디렉터리에 저장하고, 이름은 `fig{순번}-{설명}.png` 형식으로 합니다
5. **삽입**: 글에서는 `![설명](../../assets/{주제약칭}/fig{순번}-{설명}.png)` 로 참조합니다

### 네 번째 작업: 최종 파일 산출

확정 원고를 md 파일로 저장하고, 파일 끝에 논문/자료 원문 링크를 첨부합니다.

```markdown
**논문 원문:**
- arXiv: {링크}
```

## 글쓰기 레드라인

1. **데이터를 지어내지 않습니다**. 인용하는 데이터는 반드시 출처가 있어야 하며, 찾을 수 없으면 '추정'이라고 표시합니다
2. **AI 말투를 쓰지 않습니다**. "함께 살펴봅시다", "주목할 만한 점은", "말하지 않을 수 없다" 같은 상투적 표현을 금지합니다
3. **과도하게 약속하지 않습니다**. 기술 글에서 '파괴적인', '혁명적인' 같은 말을 쓰지 말고, 데이터로 말합니다
4. **수식에는 반드시 쉬운 말 풀이를 붙입니다**. 모든 수식 뒤에는 "사람 말로 옮기면 바로 ……"라는 문단이 있어야 합니다
5. **수식은 반드시 LaTeX로 씁니다**. `$$...$$` 형식을 쓰고, 순수 텍스트 수식을 금지합니다
6. **삽화는 반드시 실제로 삽입합니다**. 논문 해설 글은 PDF에서 고화질 원본 그림(≥500KB)을 추출하며, `[그림X]` 같은 자리표시자를 금지합니다
7. **표의 괄호 주석은 정확해야 합니다**. 개념을 설명할 때는 정확한 정의를 쓰고, 모호한 동사-목적어 구문을 쓰지 않습니다(예: "교사를 따라 배운 텍스트"가 아니라 "텍스트의 출처가 교사임")
8. **비유는 처음부터 끝까지 일관되게 씁니다**. 글 전체에 하나의 주축 비유를 쓰고, 절마다 새 비유로 바꾸지 않습니다
9. **결말에는 반드시 전파력이 있어야 합니다**. 마지막 문장은 따로 캡처해 공유할 가치가 있어야 합니다
